# Ошибки и способы проверки

Для вывода журнала запустите OpenCode с флагом `--print-logs`.
Сообщение ошибки API может содержать причину в круглых скобках.

## Ошибка сертификата TLS

Примеры: `unable to verify the first certificate`, `self signed certificate in chain`, `CERT_SIGNATURE_FAILURE`.

Node.js может не доверять сертификатам шлюза Сбера.
Плагин использует внешний CA-бандл или встроенные сертификаты Минцифры.

1. Проверьте путь в `options.caBundle` и `GIGACHAT_CA_BUNDLE_FILE`.
2. Проверьте содержимое файла `~/.config/opencode/certs/russian_trusted_root_ca.pem`, если он существует.
3. Если внешний файл неверный, замените его или уберите этот файл для использования встроенных сертификатов.
4. Если корпоративный прокси подменяет сертификаты, добавьте его CA-сертификат к бандлу Минцифры.

Для временной диагностики можно отключить проверку:

```bash
export GIGACHAT_VERIFY_SSL="false"
```

Переменная действует, если `verifySSL` не задан в конфиге.
Если конфиг задаёт `verifySSL: true`, временно измените это поле для проверки.
После диагностики верните проверку TLS.
Команды подготовки бандла приведены в [README](../README.md#сертификаты).

## Ключ не настроен

Сообщение: `GigaChat credentials are not configured`.

Ключ отсутствует в хранилище OpenCode, настройках провайдера и переменных окружения.

1. Выполните команду:

   ```bash
   opencode providers login --provider "GigaChat (Sberbank)"
   ```

2. Выберите scope аккаунта.
3. Вставьте ключ авторизации из кабинета Sber Developers.

Если у вас отдельно Client ID и Client Secret, создайте ключ в клонированном репозитории:

```bash
npm run encode-creds
```

Альтернативный способ, через переменные окружения:

```bash
export GIGACHAT_CREDENTIALS="ВАШ_BASE64_КЛЮЧ"
export GIGACHAT_SCOPE="GIGACHAT_API_PERS"
```

## HTTP 401 или 403 при OAuth

Возможные причины: неверный ключ, неподходящий scope или ограничения доступа аккаунта.

1. Проверьте ключ. Он должен содержать `Base64(Client_ID:Client_Secret)`.
2. Сравните scope со значением в кабинете Сбера.
3. Повторите вход с правильным ключом и scope.

Для личного аккаунта используйте `GIGACHAT_API_PERS`.
Для B2B и корпоративного API используйте scope своего ключа.

Если нужен отдельный тест OAuth, выполните запрос с подставленными значениями:

```bash
curl --location --request POST 'https://ngw.devices.sberbank.ru:9443/api/v2/oauth' \
  --header 'Content-Type: application/x-www-form-urlencoded' \
  --header 'Accept: application/json' \
  --header 'RqUID: ВАШ_UUID' \
  --header 'Authorization: Basic ВАШ_BASE64_КЛЮЧ' \
  --data-urlencode 'scope=GIGACHAT_API_PERS'
```

Если curl сообщает об ошибке TLS, подготовьте CA-бандл по [инструкции в README](../README.md#сертификаты).
Добавьте к команде параметр:

```bash
--cacert "$HOME/.config/opencode/certs/russian_trusted_root_ca.pem"
```

## HTTP 413 или слишком большой запрос

Запрос может содержать слишком много текста или большие вложения.
Плагин предупреждает об отдельных текстовых частях сообщения больше 400 КБ. Предупреждение не уменьшает запрос.

1. Найдите сообщение `WARNING: Content size (...) is large` в журнале.
2. Уберите из запроса содержимое `node_modules/`, `.git/`, `dist/`, `build/` и больших журналов.
3. Передайте только файлы, нужные для задачи.
4. Проверьте вложения по [ограничениям файлов GigaChat](https://developers.sber.ru/docs/ru/gigachat/guides/working-with-files).

Ограничения вложений зависят от их типа. Не применяйте один лимит размера ко всем запросам.

## Ошибка загрузки изображения

Плагин загружает изображение через `/files` перед запросом к модели.
Если загрузка завершилась ошибкой, плагин возвращает ошибку и не отправляет текст без картинки.

1. Проверьте соединение с API или корпоративным прокси.
2. Проверьте формат файла по [документации Сбера](https://developers.sber.ru/docs/ru/gigachat/guides/working-with-files).
3. Проверьте лимиты загрузки и доступа своего аккаунта.
4. Если используется прокси, проверьте маршрут `/files` на его базовом адресе.

## HTTP 422 при работе с инструментами

Пример сообщения: `GigaChat Translation Proxy Error: Request failed with status code 422`.

Правила запроса API v1:

- Если сообщение `system` есть, оно должно быть единственным и первым.
- Результат функции в поле `content` должен содержать JSON.
- Сообщение результата `function` должно содержать имя функции в `name`.
- При вызове функции сообщение `assistant` должно сохранять `content: null`.

Плагин объединяет `system` и `developer`, преобразует результаты в JSON и восстанавливает имена по истории.

1. Прочитайте причину API в сообщении ошибки.
2. Если причина содержит `invalid function result json string`, проверьте результат инструмента.
3. Если причина связана с `name`, проверьте наличие исходного вызова инструмента в истории.
4. Если причина связана с `system`, проверьте порядок сообщений.

Подробные правила и примеры: [архитектура](ARCHITECTURE.md#вызовы-инструментов) и [формат API](GIGACHAT_API_SPEC.md).
