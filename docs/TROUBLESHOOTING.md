# Руководство по решению проблем (Troubleshooting)

Этот документ содержит решения частых проблем, с которыми вы можете столкнуться при использовании плагина GigaChat в OpenCode.

---

## 1. Проблемы с TLS-сертификатами (SSL Errors)

### Ошибка: `unable to verify the first certificate` или `self signed certificate in chain`
*   **Причина**: Node.js по умолчанию не доверяет шлюзу `ngw.devices.sberbank.ru`, так как сертификат подписан государственным удостоверяющим центром РФ (Минцифры), отсутствующим в стандартном Node.js CA-бандле.
*   **Решение**:
    1.  Плагин содержит **встроенный бандл сертификатов Минцифры** и автоматически применяет его. Если вы видите эту ошибку, убедитесь, что вы не переопределили переменную окружения `GIGACHAT_CA_BUNDLE_FILE` неверным путем.
    2.  Если вы находитесь в корпоративной сети за прокси-сервером, который подменяет SSL-сертификаты, вам может потребоваться импортировать ваш корпоративный корневой сертификат и объединить его с бандлом Минцифры.
    3.  В крайнем случае, для локального тестирования вы можете полностью отключить проверку сертификатов, установив переменную окружения:
        ```bash
        export GIGACHAT_VERIFY_SSL="false"
        ```

## 2. Ошибки авторизации и учетных данных

### Ошибка: `GigaChat credentials are not configured`
*   **Причина**: Плагин не нашел учетные данные авторизации ни в глобальном файле `opencode.json`, ни в переменных окружения.
*   **Решение**:
    1.  **Проверка настроек `opencode.json`**: Убедитесь, что параметры авторизации заданы внутри секции `provider.gigachat.options`:
        ```json
        "provider": {
          "GigaChat (Sberbank)": {
            "options": {
              "baseURL": "https://api.gigachat.local/v1",
              "credentials": "ВАШ_BASE64_КЛЮЧ_АВТОРИЗАЦИИ_ЗДЕСЬ",
              "scope": "GIGACHAT_API_PERS"
            }
          }
        }
        ```
    2.  **Запуск генератора ключа**: Для удобного кодирования Client ID и Client Secret используйте команду:
        ```bash
        npm run encode-creds
        ```
    3.  **Использование переменных окружения**: Если вы не хотите хранить ключи в файле конфигурации, экспортируйте их в вашей текущей терминальной сессии:
        ```bash
        export GIGACHAT_CREDENTIALS="ВАШ_BASE64_КЛЮЧ"
        export GIGACHAT_SCOPE="GIGACHAT_API_PERS"
        ```

### Ошибка: HTTP статус `403 Forbidden` или `401 Unauthorized` во время запроса токена
*   **Причина**: Неверные Client ID / Client Secret в Base64 строке credentials, либо несовпадение области действия API (`scope`).
*   **Решение**:
    1.  **Проверка credentials**: Убедитесь, что строка авторизации в параметре `credentials` (или в переменной `GIGACHAT_CREDENTIALS`) закодирована правильно. Это должен быть Base64 от строки `Client_ID:Client_Secret`.
    2.  **Проверка Scope**: Убедитесь, что поле `scope` указано верно. Физические лица используют только `GIGACHAT_API_PERS`. Юридические лица или B2B-кабинеты используют `GIGACHAT_API_CORP` или `GIGACHAT_API_B2B`. Указание неверного scope ведет к ошибке HTTP 403.
    3.  Попробуйте выполнить ручной тестовый запрос через `curl`:
        ```bash
        curl --location --request POST 'https://ngw.devices.sberbank.ru:9443/api/v2/oauth' \
        --header 'Content-Type: application/x-www-form-urlencoded' \
        --header 'Accept: application/json' \
        --header 'RqUID: ВАШ_UUID' \
        --header 'Authorization: Basic ВАШ_BASE64_КЛЮЧ' \
        --data-urlencode 'scope=GIGACHAT_API_PERS'
        ```

## 3. Ошибки размера запроса (Payload Too Large)

### Ошибка: HTTP статус `413 Payload Too Large` или зависание запросов
*   **Причина**: Вы отправляете в контексте запроса слишком большой объем данных (например, пытаетесь передать всю папку проекта с `node_modules` или собранными бинарниками). Лимит размера пакета в API GigaChat составляет 10 МБ.
*   **Решение**:
    1.  Обратите внимание на предупреждение плагина в логах: `[GigaCode-Plugin] WARNING: Content size (...) is large`.
    2.  Создайте или обновите файл `.opencodeignore` в корне вашего проекта и добавьте туда исключения тяжелых папок:
        ```text
        node_modules/
        .git/
        dist/
        build/
        *.log
        ```
    3.  Не отправляйте медиафайлы или архивы в текстовом чате.

## 4. Ошибки при загрузке мультимедиа (Vision)

### Ошибка: Картинка заменяется на `[Image Upload Failed]` в чате
*   **Причина**: Плагин не смог загрузить изображение на защищенное облачное хранилище Сбера через эндпоинт `/files`.
*   **Решение**:
    1.  Проверьте стабильность интернет-соединения.
    2.  Убедитесь, что отправляемое изображение имеет поддерживаемый формат (`.png`, `.jpg`, `.jpeg`, `.webp`).
    3.  Проверьте лимиты вашего тарифного плана GigaChat API на загрузку файлов.

## 5. Ошибки валидации схемы (HTTP 422 Unprocessable Entity)

### Ошибка: `GigaCode Translation Proxy Error: Request failed with status code 422`
*   **Причина**: API GigaChat требует строгого соблюдения структуры запроса:
    1. Должно быть строго одно сообщение с ролью `system` (или `developer`), расположенное на 0-й позиции (самым первым).
    2. Передача таких параметров OpenAI, как `n`, `presence_penalty`, `frequency_penalty`, вызовет ошибку схемы.
    3. Вывод результатов инструментов (сообщения с ролью `function`) должен быть оформлен в виде валидной JSON-строки. Передача неэкранированного сырого текста (например, списка файлов или консольного вывода команды) вызовет ошибку `invalid function result json string`.
*   **Решение**:
    1.  Плагин автоматически парсит массив сообщений, конкатенирует все системные сообщения в одно и помещает его на первую позицию.
    2.  Плагин автоматически проверяет вывод инструментов: если результат не является валидным JSON, плагин оборачивает его с помощью `JSON.stringify()`, исключая ошибку валидации схемы.
    3.  Если вы всё равно получаете ошибку 422, обратите внимание на подробности ошибки от API Сбербанка, которые выводятся в логах OpenCode в круглых скобках (например, `(invalid function result json string)` или `(system message must be the first message)`).
